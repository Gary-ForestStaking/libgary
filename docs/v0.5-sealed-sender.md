# v0.5 — Sealed sender (placeholder)

**Status:** architectural target — **not normative for v0**.

## Goal

Hide **sender identity** from the relay while preserving:

- abuse controls (rate limits, quotas)  
- delivery to correct mailbox  
- optional invoice/capability economics  

## v0 baseline (explicit)

In **v0**, authenticated clients reveal sender identity to the relay for routing (see [v0-protocol.md](v0-protocol.md) §1.2). E2E ciphertext still lives inside `opaque_bytes`.

## v0.5 sketch (to specify before coding)

Wire concepts (names indicative):

| Field | Visibility |
|-------|------------|
| `delivery_slot` | Relay |
| `anonymous_credential` or **rate token** | Relay verifies **without** learning stable sender id |
| `opaque_inner` | Relay ignores |

Research directions:

- blind signatures / anonymous credentials  
- rotating sender attestations  
- per-invite **capability credits** (aligned with invite-only abuse model)  

## Dependencies

Lock **after**:

1. Double Ratchet vectors stable ([v0-protocol.md](v0-protocol.md) §8).  
2. Invite bootstrap UX stable ([v0-invite-uri.md](v0-invite-uri.md)).  
3. Relay envelope padding + quotas operational ([v0-protocol.md](v0-protocol.md) §6).

## Non-goals

- Perfect anonymity against global passive adversaries (Tor is a different layer).  
- Hiding traffic timing without cover traffic / batching ([privacy-architecture.md](privacy-architecture.md)).
